# 設計決策紀錄

> 格式依助教要求：**需求 → 候選 → 證據 → 選擇 → 代價 → 何時重新評估**。
> 協議細節見 [PROTOCOL_V3.md](./PROTOCOL_V3.md)；這份文件說明「為什麼這樣選」。

---

## D1　開獎亂數的另一半由誰提供

**需求**
- 投注鎖定時，必須存在一份玩家**無法控制、也無法預知**的熵。
- 不引入需要長期維運的後端。
- 在測試網上零額外費用即可運作。

**候選與證據**

| 候選 | 證據 | 結論 |
|---|---|---|
| (a) v2 雙種子：玩家種子＋「莊家」種子，兩個都由玩家瀏覽器產生 | 助教 T03 在本機重現：先算結果再押注，3 局全勝 | ✗ 協議本身被破解 |
| (b) 當前區塊變數（`block.prevrandao`、`blockhash(block.number-1)`） | 下注交易執行時就能讀到。玩家可以部署一個「輸了就 revert」的合約來重試，或在簽署前就預測出來（Atzei 等 [9]） | ✗ |
| (c) **玩家承諾 ＋ 下注後下一個區塊的雜湊** | 下注時該區塊還不存在。回歸測試：攻擊者用下注當下能拿到的最新區塊雜湊去預測，40 局無法全勝，每局預測值都不等於實際結果 | ✓ 採用 |
| (d) Chainlink VRF | 官方文件 [S10、S11]：需要建立並儲值訂閱、非同步回呼、設定確認數；要信任預言機網路持續可用 | 上主網時的升級方向 |
| (e) 獨立莊家伺服器＋簽章（真正的雙方 Commit-Reveal） | 需要架設並維運後端；莊家必須一直在線；莊家可能在看到結果後拒絕揭露，需要押金機制處理 | 工程量最大，且違反「無後端」的前提 |

**選擇**：(c)

**代價**（要能在口試時說出來）
1. **出塊者串通**：產出開獎區塊的出塊者，可以調整區塊內容或不出塊來影響雜湊。單獨行動時他不知道玩家的種子，無法導向特定結果；但如果**玩家把種子交給他**，兩人就能挑選結果。Slither 的 `weak-prng` 標出的正是這一點。PoS 下放棄一個 slot 的成本，大約只是該 slot 的出塊獎勵與手續費。注金一旦超過這個量級，串通就變成有利可圖（Bonneau 等 [15] 對 PoW 做過同類分析）。
2. **期限**：EVM 只能讀最近 256 個區塊的雜湊，所以必須在約 51 分鐘內結算。
3. **延遲**：至少要等一個區塊（Sepolia 約 12 秒）才能開獎。
4. **重組**：在 finality 之前若發生重組，開獎區塊被替換，結果可能改變（見 PROTOCOL_V3 §11）。

**何時重新評估**
- 部署到主網，或注金量級接近一個 slot 的獎勵
- 需要多人對賭
- 需要「下注當下就開獎」的體驗

符合以上任一情況時，改用 (d) 或 (e)。

## D2　種子與熵要存在哪裡

**需求**：第三方要能拿到完整證據，而且不能依賴歷史日誌查詢（公開 RPC 經常限制 `eth_getLogs` 的範圍）。

**候選與證據**

| 候選 | 證據 |
|---|---|
| 只留在結算交易的 calldata（v2 做法） | v2 驗證常常拿不到種子，只能部分驗證（助教 T09、R06） |
| 寫在 event | 驗證時仍然要用 `eth_getLogs` 查詢 |
| **寫進 storage** | 用 `eth_call` 呼叫 `getBet()` 一次就能讀到；E2E 測試與命令列工具都只靠這個呼叫完成完整驗證 |

**選擇**：寫進 storage

**代價**：`settleBet` 約多 3 萬 gas。但因為 `placeBet` 變便宜，一局總計反而比 v2 少約 2 萬（見 `contracts/ANALYSIS.md`）。

**何時重新評估**：主網上 gas 成為瓶頸時，改成 event，並另外保存部署區塊與結算交易 hash 作為索引。

## D3　期限要用區塊高度還是時間

**需求**：期限的意義要明確，而且結算與宣告過期不能同時都有效（助教 T04）。

**證據**：熵本身就受「256 個區塊」的限制；`block.timestamp` 由出塊者在規則範圍內填寫，語義上和「區塊序號」是不同的東西。

**選擇**：區塊高度。可以結算的區間是 `revealBlock < 區塊 ≤ revealBlock + 256`；可以宣告過期的區間是 `> revealBlock + 256`。兩者互斥。

**代價**：實際經過的時間不固定，有 slot 沒出塊時會變長。

**何時重新評估**：換到出塊時間差異很大的鏈時。

## D4　賠付方式：即時轉帳還是記帳後提領

**需求**：玩家不需要額外操作就能收到錢；單一收款方失敗時，不能影響其他人。

**證據**
- 測試「拒收 ETH 的玩家只會卡住自己那一局，不影響其他玩家結算」
- 測試「收款時重入只拿到一次賠付」

**選擇**：即時轉帳。轉帳失敗時整筆交易回滾，這一局維持 Placed。

**代價**：用「拒收 ETH 的合約」下注的玩家，贏了也無法結算，最後只能過期。一般錢包（EOA）沒有這個問題。

**何時重新評估**：要支援合約錢包或帳戶抽象的使用者時，改成記帳後提領。

## D5　「贏」的定義

**需求**：合約事件、遊戲畫面、統計、實驗室的定義必須一致（助教 R07）。

**證據**：v2 合約的 `won` 是 `payout > 0`，Plinko 頁面卻用「倍率 ≥ 1」判斷。結果是 0.5× 被合約算成贏、1.0× 被頁面算成贏，實際上前者淨輸、後者不輸不贏。

**選擇**：
- **淨贏**：賠付 > 注金
- **平**：賠付 = 注金（退回本金）
- **輸**：其他情況

全系統共用 `netResult()`；合約事件的 `won` 也改成 `payout > amount`。

**代價**：舊紀錄的勝率與新紀錄的定義不同，混在一起看會有落差。

## D6　v2 合約怎麼處理

**需求**：舊局仍然要能查驗；不能讓前端繼續對有缺陷的合約下注。

**證據**：v2 是不可升級合約（沒有代理），改原始碼不會改變已部署的程式（助教 07）。

**選擇**
- 部署 v3 到新地址。
- v2 保留為唯讀，驗證工具可以選「v2（已停用）」核對舊局。
- 若前端設定仍指向 v2 地址，自動停用下注。
- 所有部署記錄在 `contracts/deployments/<network>.json`，一局的完整識別是 chainId ＋ 合約地址 ＋ betId ＋ 規則版本。

**代價**：v2 的舊局只能證明紀錄自洽，**不能**證明當時沒有被預選。

## D7　21 點與猜數字暫不修改協議

**需求**：助教建議「先縮到一個簡單遊戲，建立清楚的協議」。

**證據**：這兩款有**隱藏資訊**（莊家暗牌、密碼），必須在玩家行動期間保密。v3 的方式一開獎就讓玩家知道全部資訊，所以沒辦法解決「偷看」的問題。真正的解法是逐張揭露或引入獨立莊家，屬於另一種狀態機。

**選擇**
- 合約不改（無金流，只做公平性展示）。
- 修正驗證器，改成依完整行動重播（T06）。
- 修正亂數映射（R05）。
- 在介面與文件明確寫出「玩家可在行動前算出結果」。

**代價**：這兩款仍然不具防作弊能力。

**何時重新評估**：v3 的下注協議完成比較實驗之後。

## D8　為什麼現在不換鏈

**需求**：先確認問題出在哪一層。

**證據**：助教指出，換到更快或更便宜的鏈，並不能修好亂數權限、驗證公式與本地紀錄的問題；先修協議再比較鏈，否則「比較到的只是同一個有缺陷協議在不同網路上的速度」。

**選擇**：保留 Ethereum Sepolia 作為基準。鏈的比較（助教交付物 A、D）排在 v3 部署之後。

**代價**：還沒有 L2 的實測成本與延遲數據。

**後續（2026-10-18）**：v3 已部署到 Sepolia，L1 實驗有效樣本 38 局（原定 100 局，見 [experiments/](./experiments/README.md)）；鏈的候選比較見 [CHAIN_COMPARISON.md](./CHAIN_COMPARISON.md)。L2 與 VRF 的實測仍缺測試幣。

## D9　賠率表維持現狀

**需求**：助教 T08 要求說明賠率表的設計目標、方差、尾端賠付、對資金池的影響、扣 gas 後的期望值。

**候選**
1. 先校準賠率（例如拉霸對子改 1.8×），再重新部署。
2. 維持現在的賠率，只把分析做完、把問題寫清楚。

**證據**（[ODDS_ANALYSIS.md](./ODDS_ANALYSIS.md)）
- 拉霸 RTP 105.56%，**莊家長期虧損**；骰子、硬幣、Crash、Limbo、左輪 RTP 100%，莊家沒有優勢；輪盤單號 81.08%、轉盤 87.5% 偏低。
- 改任何一個倍率都要同步改 `random.js` 與合約 `resolve()`，並**重新部署**；v3 才剛部署、地址已寫進 CI 與專題本。
- 本專題的目標是「結果可驗證」，不是經營賭場；Sepolia 的 ETH 沒有市場價值。

**選擇**：2。不改賠率，也不改合約裡 `% 6`、`% 37` 約 10⁻⁹ 的取模偏差。

**代價**：拉霸會讓資金池長期流失；任何人反覆玩拉霸，資金池的期望變化是每注 −5.56%。資金池不足時合約會拒絕新下注（不變量 I1），不會出現賠不出來的局。

**何時重新評估**：下一次因其他原因必須重新部署合約時一併處理。建議值：拉霸對子 1.8×（RTP 97.22%）；骰子、硬幣改 1.96×（RTP 98%）；Crash／Limbo 在公式加 1% 莊家優勢。

## D10　開獎區塊只往後看 1 個區塊

**需求**：開獎熵要在下注之後才產生，而且等待時間要短。

**候選**
1. `revealBlock = 下注區塊 + 1`（目前）。
2. 往後看更多區塊，例如 EIP-4399 建議的至少 4 個 epoch（約 25 分鐘）。
3. 改用 VRF。

**證據**：EIP-4399 指出每個提議者對 RANDAO 有 1 bit 影響力，並建議應用使用「有足夠前瞻的未來亂數」。前瞻越長，下注當下越難知道開獎區塊由誰提議，串通越難事先安排；但 `blockhash` 只能取最近 256 個區塊（約 51 分鐘），玩家也要等更久。Sepolia 實測中，從下注確認到開獎區塊產生的中位數為 11.6 秒（P95 13.9 秒），見 [experiments/](./experiments/)。

**選擇**：1。殘餘風險（玩家與出塊者串通）寫進 PROTOCOL §7，並由 Slither `weak-prng` 標出。

**代價**：出塊者若與玩家串通，可以靠放棄出塊或調整區塊內容重抽。

**何時重新評估**：若要處理有價值的資產，或搬到 L2，改用 VRF（見 [CHAIN_COMPARISON.md](./CHAIN_COMPARISON.md)）。
