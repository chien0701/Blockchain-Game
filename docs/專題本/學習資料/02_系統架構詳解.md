## 1. 設計原則：無自建後端

### 1.1 正式寫法

> 靜態網頁前端＋區塊鏈智能合約＋外部 RPC 服務，**不另行建置自有應用程式後端或中心化遊戲資料庫**（簡稱「無自建後端架構」）。

### 1.2 為什麼這樣設計

| 如果有後端… | 會發生什麼 |
|---|---|
| 後端保存遊戲紀錄 | 我們就能偷改紀錄，等於回到原本的信任問題 |
| 後端幫忙開獎 | 我們就能在看到下注之後才決定結果 |
| 後端保管莊家種子 | 需要一台永遠在線、保管秘密的伺服器；第一版就是因為沒有它而失敗 |

所以「不做後端」不是偷懶，是**刻意的設計**：平台手上沒東西，才沒有東西可以動手腳。

### 1.3 代價

- 未結算那一局的種子只能存在玩家瀏覽器（見第 2 節）。
- 每個動作都要上鏈，要付 Gas、要等區塊。
- 第二份亂數不能靠「莊家」提供，只能用區塊雜湊，因此留下「出塊者串通」的殘餘風險。

> ⚠ 不要說「Serverless」。Serverless 是指雲端廠商代管的執行環境，跟「我們沒有自建後端」不是同一件事。

> 🗣 「為什麼不做後端喔？因為一做後端，資料又在我們手上了嘛，那玩家還是得相信我們，等於白做。所以我們乾脆不做，代價就是種子要存在玩家自己的瀏覽器，還有每一步都要上鏈。」

## 2. 資料放在哪（三類資料）

| 類別 | 具體內容 | 存放位置 | 遺失後果 |
|---|---|---|---|
| **權威資料** | 下注時：承諾、下注金額、注型、開獎區塊；結算時：種子、盲化值、熵、finalRandom、結果、賠付 | FairBet 合約的儲存區 | 不會遺失；任何人可用 `getBet()` 讀取 |
| **便利性資料** | 最近 50 局的遊戲紀錄、介面偏好 | 瀏覽器 localStorage（`fairchain_game_*`、`fairchain_index`） | 不影響已結算局的驗證 |
| **待結算之暫存秘密** | 還沒結算那一局的種子與盲化值 | 瀏覽器 localStorage（`fairchain_pending`） | 該局無法結算；超過期限後下注金額留在資金池 |

### 為什麼要把種子寫進合約？

v3 結算時，會把種子、盲化值、熵、結果**全部寫進合約儲存區**。這樣驗證者只要呼叫一次 `getBet(betId)` 就拿到所有證據。

- **好處**：不用去翻歷史交易紀錄（第二版的種子只存在交易的輸入資料裡，很多 RPC 節點限制查詢歷史日誌，常常只能「部分驗證」）。
- **代價**：寫入儲存區很貴。`settleBet` 因此多花約 3 萬 gas；Sepolia 啟用 EIP-8037 後，寫入新儲存槽的成本又提高，每局實測約 111 萬 gas。

> 🗣 「網站倒掉也沒關係啦，已經結算的局所有證據都在鏈上，誰都可以讀。比較麻煩的是還沒結算的那局，因為種子只在玩家瀏覽器裡，玩家要是把瀏覽器資料清掉，那局就沒辦法結算了。」

```
表現層　　　 React 頁面與元件 ……………… 畫面、按鈕
   ↓
應用邏輯層　 useBetting、random.js、registry.js … 一局的流程、算結果、遊戲清單
   ↓
密碼學層　　 crypto.js ………………………… 產生種子、算承諾
   ↓
錢包層　　　 WalletContext.jsx …………… MetaMask、切換網路
   ↓
鏈上互動層　 contract.js ………………………… 呼叫合約、唯讀 Provider
   ↓
區塊鏈層　　 FairBet.sol、GameCommitReveal.sol … 收注、驗證、判定、賠付
```

| 層級 | 檔案 | 負責什麼 | 一句話記憶 |
|---|---|---|---|
| 表現層 | `src/pages/`、`src/components/` | 畫面呈現、使用者操作 | 「看得到的」 |
| 應用邏輯層 | `src/hooks/useBetting.js` | 一局下注的流程狀態機：下注 → 等區塊 → 結算 → 比對 | 「流程的大腦」 |
| | `src/games/random.js` | 結果引擎 `resolveBet()`：用 finalRandom 算結果與賠付 | 「和合約同一套公式」 |
| | `src/games/registry.js` | 11 款遊戲的清單，大廳、路由都從這裡讀 | 「遊戲目錄」 |
| 密碼學層 | `src/utils/crypto.js` | `generateSeed()`、`generateSalt()`、`commitHash()`、`combineSeeds()` | 「算雜湊的地方」 |
| 錢包層 | `src/context/WalletContext.jsx` | 連 MetaMask、偵測網路錯誤、取得簽署者 | 「簽名用」 |
| 鏈上互動層 | `src/utils/contract.js` | `placeBetOnChain()`、`settleBetOnChain()`、`waitForBlock()`、`getBetV3()`、**唯讀 Provider** | 「跟鏈講話」 |
| 區塊鏈層 | `contracts/contracts/` | 兩份合約 | 「真正的裁判」 |

另外兩個重要模組：

| 檔案 | 做什麼 |
|---|---|
| `src/utils/storage.js` | **所有** localStorage 讀寫集中在這裡，其他檔案不直接碰 localStorage |
| `src/utils/verify.js` | 驗證判定邏輯；**不連網路**，只負責比對，所以可以單獨測試 |

### 唯讀 Provider 為什麼重要

一般讀鏈上資料要透過錢包；唯讀 Provider 改用**公開 RPC 節點**直接讀。所以第三方驗證者**不用裝 MetaMask、不用有帳號、不用付錢**就能驗證。這直接對應研究目的三「無須許可之驗證」。

> 🗣 「前端我們分六層啦，最上面是畫面，最下面是合約。比較特別的是鏈上互動那層有做一個唯讀的連線，用公開節點去讀資料，所以要驗證的人連 MetaMask 都不用裝。」

## 4. 合約內部長什麼樣子（FairBet v3）

### 4.1 每一局存了什麼（`Bet` 結構）

| 欄位 | 意思 | 何時寫入 |
|---|---|---|
| `player` | 下注的玩家地址 | 下注 |
| `gameType`、`betType`、`param` | 哪個遊戲、哪種注、參數（例如押哪個號碼） | 下注 |
| `amount` | 下注金額 | 下注 |
| `playerCommit` | 承諾 `keccak256(seed‖salt)` | 下注 |
| `revealBlock` | 開獎區塊＝下注區塊＋1 | 下注 |
| `state` | 狀態（見 4.2） | 每次改變 |
| `playerSeed`、`playerSalt` | 揭露的種子與盲化值 | 結算 |
| `entropy` | 開獎區塊的雜湊 | 結算 |
| `finalRandom` | `keccak256(seed‖entropy)` | 結算 |
| `outcome`、`payout` | 結果與賠付 | 結算 |

### 4.2 每一局的狀態變化

```
None ──placeBet()──▶ Placed ──settleBet()──▶ Settled（已開獎、已賠付）
                       │
                       └── 超過 revealBlock + 256 ──claimExpired()──▶ Expired（未開獎，下注金額留在資金池）
```

- 可結算區間：`revealBlock < 目前區塊 ≤ revealBlock + 256`
- 可宣告過期：`目前區塊 > revealBlock + 256`
- 兩個區間**互斥**，不會出現「同一個區塊兩邊都能做、誰先送誰贏」。
- **Expired 是獨立狀態**，不會跟 Settled 混在一起，驗證者不會把沒開獎的局誤認成公平局。

### 4.3 主要函式

| 函式 | 誰能呼叫 | 做什麼 |
|---|---|---|
| `placeBet(gameType, betType, param, commit)` | 任何人（附下注金額） | 檢查注型合法、承諾沒用過、資金池賠得起，鎖定最大賠付，記下開獎區塊 |
| `settleBet(betId, seed, salt)` | **只有該局玩家** | 檢查時間區間與承諾，取區塊雜湊、算結果、先改狀態再轉帳 |
| `claimExpired(betId)` | 任何人 | 逾期局標成 Expired，解除鎖定 |
| `withdraw(amount)` | 只有合約擁有者 | 只能提領「餘額減去已鎖定額」的部分 |
| `getBet(betId)` | 任何人（唯讀） | 一次取得該局所有證據 |
| `betIdByCommit(commit)` | 任何人（唯讀） | 用承諾反查局號；也用來禁止重複使用同一個承諾 |
| `maxPayout(...)`、`resolve(...)`、`crashBps(...)` | 任何人（純函數） | 算最大賠付、算結果、算 Crash 倍率；前端用同一套公式 |

### 4.4 幾個常數

| 常數 | 值 | 為什麼 |
|---|---|---|
| `REVEAL_WINDOW` | 256 | EVM 只能讀最近 256 個區塊的雜湊 |
| `RULES_VERSION` | 3 | 標示規則版本，驗證器依版本選擇演算法 |
| `CRASH_CAP` | 1,000,000 bps（100 倍） | Crash 倍率上限，保護資金池 |
| `owner` | `immutable` | 部署後不能更改 |

### 4.5 GameType 的順序為什麼不能改

合約裡遊戲類型是一個列舉：`Dice, Coin, Roulette, Slots, Crash, Limbo, Wheel, Plinko, Revolver`，在鏈上存的是編號（0–8）。前端也是寫死用這些編號。**如果中間插一個新遊戲，所有編號都會錯位**，舊局的驗證也會算錯，所以新增遊戲只能加在最後面。

> 🗣 「合約裡每一局就是一筆紀錄，下注的時候先存承諾跟開獎區塊，結算的時候再把種子、雜湊、結果都補進去。狀態就四種：還沒下注、已下注、已結算、過期。過期是獨立一個狀態，才不會跟正常開獎的混在一起。」

## 5. 第二份合約：GameCommitReveal

| 項目 | 內容 |
|---|---|
| 用在哪 | 二十一點、猜數字 |
| 有沒有金流 | 沒有 |
| 狀態 | `None → Committed → Revealed` |
| 能證明什麼 | 揭露的種子和當初承諾的一樣，**沒有事後偷換** |
| 不能證明什麼 | 兩把種子都在玩家瀏覽器產生，無法證明來源獨立；玩家可先算出牌堆或密碼 |

**為什麼不放進 FairBet？** 本系統是「拿一次亂數、一次結算」的模式。二十一點中途要決定補不補牌、牌堆要保密，需要多階段的鏈上流程，這次沒有設計，所以只做公平性展示。**這是設計範圍的限制，不是技術上做不到。**

> 🗣 「二十一點不是不能上鏈啦，是我們的系統只做一次算完的模式，二十一點中間要讓玩家決定，還要藏牌，那要做成好幾個階段的流程，我們這次沒做，所以就先拿另一個合約做展示。」

## 6. 一局下注在程式裡怎麼跑（圖三）

```
遊戲頁         useBetting       storage.js       contract.js      MetaMask       FairBet v3
  │ 按下注 ───▶ │                  │                 │               │               │
  │            │ 產生種子、算承諾    │                 │               │               │
  │            │ ① 先存未完成紀錄 ──▶│                 │               │               │
  │            │ ② placeBet ─────────────────────────▶│ 請求簽名 ────▶│ ─────────────▶│ 記錄、鎖定、revealBlock
  │            │ ③ 寫回局號 ────────▶│                 │               │               │
  │            │ ④ 等開獎區塊 ────────────────────────▶│ 每 2 秒查一次區塊高度           │
  │            │ ⑤ settleBet ────────────────────────▶│ 請求簽名 ────▶│ ─────────────▶│ 驗承諾、開獎、轉帳
  │            │ ⑥ 用 random.js 在本機重算，和合約結果比對                              │
  │            │ ⑦ 刪除未完成紀錄 ──▶│                 │               │               │
  │ ⑧ 存完整紀錄 ─────────────────▶│                 │               │               │
```

**最關鍵的是第 ① 步：送出交易之前，先把種子存進瀏覽器。** 如果反過來（先送交易才存種子），交易送出後頁面當掉，種子就不見了，錢卻已經進了合約。

### 中斷了怎麼辦（恢復機制）

| 情況 | 系統怎麼處理 |
|---|---|
| 下注後重新整理頁面 | 從 `fairchain_pending` 讀回種子，繼續等區塊、結算同一局 |
| 第二筆交易（結算）失敗或拒簽 | 該局保留在大廳的「未完成的下注」，之後再結算**同一局**，不會重複下注 |
| 本機沒存到局號 | 用承諾呼叫 `betIdByCommit()` 反查局號 |

Sepolia 實測模擬了 3 次「下注後頁面關閉」，2 次成功恢復；失敗那次是 RPC 節點還沒同步，網站遇到這種情況會保留紀錄稍後再查。

> 🗣 「我們有一個小細節是，送交易之前就先把種子存起來。不然交易送出去頁面就當了，種子不見，錢又已經進合約，那就慘了。中斷之後可以在大廳的『未完成的下注』繼續結算同一局。」

## 7. 兩種執行模式

| 模式 | 什麼時候 | 行為 |
|---|---|---|
| **bet**（真實下注） | 有設定 v3 合約地址＋已連 MetaMask＋網路正確 | 真的上鏈、真的扣錢與賠付 |
| **mock**（模擬） | 其他所有情況：沒裝 MetaMask、沒連錢包、地址沒設定 | 同一套流程，但開獎的熵改由本機產生，不上鏈、沒有金流 |

- 模擬模式在畫面上會明確標示「模擬模式」及原因。
- 如果設定檔指向舊的 v2 合約（有協議缺陷），前端會**自動停用下注**。

> 🗣 「沒連錢包也可以玩啦，會進到模擬模式，流程一模一樣，只是亂數在本機產生、不會上鏈，畫面上也會標得很清楚。」

## 8. 驗證器的架構（3.5）

### 8.1 三個檔案分工

| 檔案 | 角色 |
|---|---|
| `src/utils/verify.js` | **判定邏輯**：輸入鏈上資料＋區塊雜湊，輸出判定。不連網路，可以單獨測試 |
| `src/utils/contract.js` | **取資料**：`getBetV3()` 讀合約、`getBlockHash()` 另外向 RPC 取區塊雜湊 |
| `src/pages/Verifier.jsx` | **畫面**：網站上的驗證頁 |
| `scripts/verify-bet.mjs` | **命令列工具**：不經過網站，直接用同一個 `verify.js` 驗證 |

### 8.2 三種驗證模式

| 模式 | 資料來源 | 要錢包嗎 | 要信任本網站嗎 | 能驗什麼 |
|---|---|---|---|---|
| 本地紀錄 | 瀏覽器 localStorage | 否 | 是 | 結論最多到「未完成」 |
| 鏈上・公平局 | GameCommitReveal | 否 | 否 | 只能證明揭露值與承諾一致 |
| 鏈上・下注局 | FairBet v3 | 否 | 否 | 完整五項 |
| 命令列工具 | 任一 RPC | 否 | 否（不經網站） | 完整五項 |

### 8.3 五項證據與判定

1. 承諾：`keccak256(seed‖salt)` 等於鏈上承諾嗎？
2. 區塊熵：合約記錄的熵，等於**另外向 RPC 取得**的開獎區塊雜湊嗎？（不採信合約自己記的）
3. 最終隨機數：`keccak256(seed‖區塊雜湊)` 等於 finalRandom 嗎？
4. 結果：用 `resolveBet()` 重算，跟合約一樣嗎？
5. 賠付：重算的賠付金額跟合約一樣嗎？

| 判定 | 條件 |
|---|---|
| 通過（verified） | 五項全部取得且吻合 |
| 失敗（failed） | 任何一項不符 |
| 未完成（incomplete） | 任何一項拿不到證據（例如 RPC 取不到區塊雜湊）——**不算通過** |
| 已過期（expired） | 該局逾期未開獎 |
| 未結算（pending） | 該局還沒結算 |

> 🗣 「驗證的時候我們刻意不相信合約自己記的熵，會另外去問 RPC 那個區塊的雜湊再比一次。然後只要有一項資料拿不到，就判『未完成』，不會硬說它通過。」

## 9. 部署與開發架構（3.6）

### 9.1 網站怎麼上線


| 取捨 | 選了什麼 | 換來什麼 | 付出什麼 |

## 12. 練習題（口語版參考答案）

**Q1. 畫或說出你們的系統架構。**
> 「就是三塊嘛：瀏覽器裡的網頁、Sepolia 上的兩份合約，中間靠 MetaMask 簽交易、靠公開 RPC 讀資料。我們自己沒有伺服器。」

**Q2. 為什麼合約要分兩份？**
> 「FairBet 是給一次就能算完結果的 9 種遊戲用的，有真的下注和賠付；二十一點跟猜數字要中途決定、要藏資訊，不在我們單次結算的範圍，所以用 GameCommitReveal 做展示，沒有金流。」

**Q3. 一局在合約裡有哪些狀態？**
> 「四種：None、Placed、Settled、Expired。下注變 Placed，結算變 Settled，超過 256 個區塊沒結算就可以被改成 Expired。」

**Q4. 為什麼送交易前要先存種子？**
> 「因為如果先送交易，頁面剛好當掉，種子就不見了，但錢已經進合約，那局就沒辦法結算。先存起來就可以之後續做同一局。」

**Q5. 驗證器為什麼不直接相信合約記錄的熵？**
> 「因為要驗證的就是合約有沒有算對嘛，所以我們另外去問 RPC 那個區塊的雜湊，自己比一次，比較公正。」

**Q6. 你們怎麼確定前端算的跟合約算的一樣？**
> 「合約測試會直接載入前端的 random.js，跟 Solidity 合約比對結果和賠付，所以測到的就是網站真的在跑的程式，不是另外寫的模型。」

**Q7. GameType 的順序為什麼不能隨便改？**
> 「因為鏈上存的是編號，前端也寫死這些編號，中間插一個進去，後面全部錯位，舊的局也會驗錯，所以只能加在最後面。」

**Q8. 網站被駭了，玩家會怎樣？**
> 「已經結算的局不影響，證據都在鏈上，可以用命令列工具或其他 RPC 驗證，不用經過我們網站。不過網站被改的話，可能會誘導玩家簽奇怪的交易，所以玩家簽名前還是要看清楚。」

## 13. 容易答錯的地方

| 錯誤說法 | 正確說法 |
|---|---|
| 我們是 Serverless | 無自建後端架構 |
| 網站倒了就全部沒辦法驗證 | 已結算的局仍可從鏈上驗證；只有未結算的局受影響 |
| 驗證要連錢包 | 用唯讀 Provider，不需要錢包 |
| 驗證時拿合約記錄的熵就好 | 要另外向 RPC 取區塊雜湊比對 |
| 拿不到資料也算通過 | 判「未完成」，不算通過 |
| 二十一點技術上不能上鏈 | 不在本系統單次結算模式的設計範圍 |
| 過期就是結算失敗 | 過期是獨立的 Expired 狀態，和 Settled 分開 |
