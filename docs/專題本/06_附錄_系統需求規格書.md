# 附錄一、系統需求規格書（SRS）

**系統名稱：** FairChain 區塊鏈可驗證公平博弈系統
**需求代碼前綴：** FC（FairChain）
**版本：** 1.0
**日期：** 中華民國 115 年 ○ 月 ○ 日

---

## 1. 系統概述

### 1.1 目的

本文件規範 FairChain 系統之功能需求、模組介面需求、非功能需求與設計實作限制，作為系統開發、測試與驗收之依據。

### 1.2 範圍

FairChain 為一套部署於 Ethereum Sepolia 測試網之可驗證公平博弈系統，包含瀏覽器前端應用程式與兩份智能合約。系統提供 11 款遊戲，其中 9 款支援以測試代幣進行鏈上下注與自動結算，全部遊戲皆支援公平性驗證。

**本系統不涉及真實金流**，所有交易使用不具經濟價值之測試代幣，供學術研究與技術展示之用。

### 1.3 名詞定義

| 名詞 | 定義 |
|---|---|
| 種子（Seed） | 由參與方產生之 256 位元隨機值 |
| 盲化值（Salt） | 附加於種子之 256 位元隨機值，用於強化承諾之隱藏性 |
| 承諾（Commitment） | `keccak256(seed‖salt)`，於揭露前公開之雜湊值 |
| 開獎區塊（revealBlock） | 下注交易所在區塊之下一個區塊；其雜湊作為第二份熵 |
| 熵（entropy） | `blockhash(revealBlock)` |
| 最終隨機數（finalRandom） | `keccak256(seed‖entropy)`，決定遊戲結果之唯一輸入 |
| 純函數（Pure Function） | 輸出僅由輸入決定，無外部狀態依賴之函數 |
| 基點（bps） | 倍率單位，10000 bps = 1 倍 |
| RTP | Return-To-Player，長期返還率 |

## 2. 功能需求

### 2.1 承諾與揭露

| 代碼 | 需求描述 | 優先級 |
|---|---|---|
| FC-F-001 | 系統應於每局開始前，為玩家產生 256 位元之隨機種子與盲化值，並使用密碼學安全亂數產生器（CSPRNG） | 必要 |
| FC-F-002 | 系統應計算承諾值 `keccak256(seed‖salt)`，並於揭露前僅將承諾值送上區塊鏈，不得洩漏種子明文 | 必要 |
| FC-F-003 | 系統應於同一局內全程維持種子不變，重玩時方可重新產生 | 必要 |
| FC-F-004 | 智能合約應於揭露階段重新計算並驗證玩家承諾，不符須拒絕該次交易並回滾狀態 | 必要 |
| FC-F-004a | 下注介面**不得**接受玩家以外之任何亂數輸入；任何參與者皆不得能代替他方提交熵 | 必要 |
| FC-F-004b | 同一承諾不得用於兩局 | 必要 |
| FC-F-005 | 智能合約應以 `keccak256(seed‖blockhash(revealBlock))` 合成最終隨機數，其中 revealBlock 為下注區塊之下一個區塊；結算僅能於 revealBlock 之後執行 | 必要 |

| 代碼 | 需求描述 | 優先級 |
|---|---|---|
| FC-F-010 | 系統應提供 11 款遊戲，並於遊戲大廳統一列出 | 必要 |

| FC-F-012 | 每款可下注遊戲應允許使用者選擇注型與下注金額，並於下注前顯示可能之賠付金額 | 必要 |

| FC-F-014 | 智能合約應於結算時獨立重算遊戲結果，不得採信前端所回報之結果 | 必要 |

| FC-F-021 | 鏈上驗證模式應使用公開 RPC 之唯讀連線，**不得要求使用者安裝錢包或擁有帳號** | 必要 |

## 3. 模組介面需求

| 代碼 | 需求描述 |
|---|---|
| FC-I-001 | 前端與智能合約之間應透過 ethers.js v6 進行互動，所有合約呼叫須集中封裝於 `utils/contract.js` 單一模組 |
| FC-I-002 | 前端承諾計算須使用 `ethers.solidityPackedKeccak256(['bytes32','bytes32'], [a, b])`，須與合約之 `keccak256(abi.encodePacked(a, b))` 於位元層級完全等價 |
| FC-I-003 | 遊戲結果計算須集中於 `games/random.js` 單一模組，且須與合約 `_resolve()` 之公式逐位元一致 |
| FC-I-004 | 遊戲清單須由 `games/registry.js` 作為單一真相來源，供大廳、首頁與路由共同引用 |
| FC-I-005 | 本機儲存之讀寫須集中於 `utils/storage.js`，不得於其他模組直接存取 localStorage |
| FC-I-006 | 錢包狀態須由 `WalletContext` 以 React Context 提供全域存取 |
| FC-I-007 | 智能合約 `FairBet` 須提供 `getBet(betId)` 公開唯讀介面，供第三方查詢完整下注資料 |
| FC-I-008 | 智能合約須於結算完成時發出 `BetSettled` 事件，包含 `won`（賠付大於注金）、`outcome`、`entropy`、`finalRandom`、`payout` 欄位 |
| FC-I-010 | 智能合約須將種子、salt、熵、finalRandom、結果與賠付寫入儲存區，使第三方僅以 `getBet()` 即可完整驗證；並公開純函數 `resolve()` |
| FC-I-011 | 前端 ABI 須集中於 `src/config/abi.js`，並以自動化測試檢查與合約編譯產物一致 |
| FC-I-009 | `FairBet` 之 `GameType` 列舉順序須與前端硬編碼之數值對應；**修改時只得於尾端追加，不得調整既有順序** |

## 4. 非功能需求

### 4.1 安全性

| 代碼 | 需求描述 |
|---|---|
| FC-N-001 | 智能合約須採用 Checks-Effects-Interactions 模式，於外部轉帳前完成所有狀態更新，以防止重入攻擊 |
| FC-N-002 | 智能合約須維護 `lockedPayouts` 鎖定機制，確保任一時點之合約餘額足以支付所有未結算下注之最大可能賠付 |
| FC-N-003 | 合約擁有者之提領功能須受 `lockedPayouts` 限制，不得提領已鎖定之資金 |
| FC-N-004 | 揭露期限以區塊高度計算：revealBlock 之後 256 個區塊內可結算，超過後任何人可宣告過期，該局狀態為 Expired（不得記為 Settled），注金留存資金池；兩區間不得重疊 |
| FC-N-004a | 前端須於送出下注前保存種子與承諾，使重整、拒簽或斷線後能續結算同一局，且重試不得重複下注 |
| FC-N-004b | 驗證工具於任一項證據無法取得時，須判為「未完成」而不得顯示「通過」 |
| FC-N-005 | 結算函數須限制僅該局玩家可呼叫 |
| FC-N-006 | 種子與盲化值須以密碼學安全亂數產生器產生，不得使用 `Math.random()` |
| FC-N-007 | 部署私鑰須存放於 `.env` 並列入 `.gitignore`，不得進入版本控制或建置產物 |
| FC-N-008 | 系統須通過 Slither 靜態分析，且不得存在高危或中危等級之漏洞 |

## 5. 設計與實作限制

| 代碼 | 限制描述 | 理由 |
|---|---|---|
| FC-D-001 | 所有可鏈上結算之遊戲結果**必須為 `finalRandom` 之純函數** | 唯有如此，智能合約方能獨立重算判定，第三方方能驗證 |
| FC-D-002 | 含玩家中途決策或隱藏資訊之遊戲不得支援鏈上下注結算，且須於介面標示其不具防作弊能力 | 違反 FC-D-001；或玩家可於行動前算出隱藏資訊 |
| FC-D-003 | 倍率須以整數基點（bps）表示，禁止使用浮點數 | Solidity 不支援浮點數運算 |
| FC-D-004 | 智能合約須使用 Solidity 0.8.0 以上版本 | 利用編譯器內建之整數溢位檢查 |
| FC-D-005 | 系統僅部署於測試網，所使用之代幣不得具有真實經濟價值 | 本系統未經專業審計，且我國法令對博弈行為有所規範 |
| FC-D-006 | 系統不得建置傳統後端伺服器或資料庫 | 保留中心化後端將使信任問題無法真正消除 |
| FC-D-007 | 本機儲存僅得存放快取與偏好設定，權威資料一律以區塊鏈為準 | 確保本機資料遺失不影響任何驗證能力 |
| FC-D-008 | 合約迴圈次數須為固定上限，不得隨資料量增長 | 避免 Gas 耗盡導致合約永久失效 |
| FC-D-009 | 部署網站之基底路徑（`vite.config.js` 之 `base` 與路由之 `basename`）須保持一致 | GitHub Pages 子路徑部署之要求 |

## 6. 操作概念

### 6.1 使用者角色

| 角色 | 說明 | 所需條件 |
|---|---|---|
| 一般玩家 | 進行遊戲、查看紀錄與統計 | 瀏覽器（模擬模式）或 MetaMask + 測試代幣（上鏈模式） |
| 第三方驗證者 | 驗證任一局遊戲之公平性 | **僅需瀏覽器，無須錢包與帳號** |
| 系統管理者 | 部署合約、注資金池、提領未鎖定資金 | 合約擁有者私鑰 |

### 6.2 典型操作流程

**流程一：玩家進行一局鏈上下注**

1. 開啟網站，點擊「連接錢包」並授權 MetaMask；
2. 若網路非 Sepolia，點擊警示橫幅之「切換網路」；
3. 進入遊戲大廳，選擇遊戲（例如 Crash）；
4. 選擇注型（目標倍率）與下注金額，畫面顯示可能賠付；
5. 點擊「下注並開獎」；系統先於本機保存種子，再請使用者於 MetaMask 確認第一筆交易（`placeBet`）；
6. 等待開獎區塊產生（畫面顯示「等待開獎區塊 #N（目前 #M）」）；
7. 於 MetaMask 確認第二筆交易（`settleBet`）；
8. 畫面顯示開獎結果、密碼學證明（種子、承諾、熵、最終隨機數）、賠付金額（贏／平／輸），以及「合約的開獎結果與賠付，和本地重算完全一致」之標記；
8a. 若中途關閉頁面或第二筆交易失敗，可於遊戲大廳之「未完成的下注」續結算同一局；
9. 紀錄自動存入本機，可於統計頁查看累積損益曲線。

**流程二：第三方驗證某一局遊戲**

1. 開啟網站之驗證頁面（**無須連接錢包**）；
2. 選擇「鏈上・下注局」模式，輸入下注編號（Bet ID）；
3. 系統以公開 RPC 讀取合約資料與結算交易；
4. 系統於本機重算並顯示三項驗證結果：
   - 承諾驗證：`keccak256(seed‖salt)` 是否等於鏈上承諾；
   - 熵驗證：合約記錄之熵是否等於向 RPC 另行取得之 revealBlock 區塊雜湊；
   - 隨機數驗證：`keccak256(seed‖熵)` 是否等於鏈上 finalRandom；
   - 結果驗證：以前端引擎重算之 outcome 是否等於合約判定之 outcome。

**流程三：管理者部署系統**

1. 於 `contracts/.env` 設定部署私鑰與 RPC 端點；
2. 執行 `npx hardhat test` 確認 38 個測試全數通過；
3. 執行部署腳本，部署兩份合約並為 `FairBet` 注入初始資金池；
4. 將合約地址更新至前端環境變數與 GitHub Actions 設定；
5. 推送至 main 分支觸發自動部署。

## 7. 使用者介面設計

### 7.1 頁面架構

| 頁面 | 路徑 | 主要內容 |
|---|---|---|
| 首頁 | `/` | 系統簡介、核心概念說明、進入大廳入口 |
| 遊戲大廳 | `/lobby` | 11 款遊戲卡片、最近 8 局紀錄 |
| 遊戲頁 | `/game/:id` | 下注面板、開獎動畫、結果與密碼學證明 |
| 驗證工具 | `/verifier` | 三種驗證模式之輸入與結果呈現 |
| 統計 | `/stats` | 總局數、勝率、損益曲線 |
| 期望值實驗室 | `/lab` | 蒙地卡羅模擬與 RTP 收斂圖 |
| 說明文件 | `/docs` | 協議原理與操作說明 |

### 7.2 介面設計原則

1. **深色主調搭配電光藍強調色**，符合區塊鏈技術產品之視覺慣例；
2. **簡約優先**，避免無意義之裝飾性小字與圖案，資訊密度以可讀性為準；
3. **狀態必須明確**：模擬模式、網路錯誤、交易等待、結果一致性等關鍵狀態皆須有明顯的視覺標示；
4. **密碼學證明必須可見**：種子、盲化值、承諾與最終隨機數應於結果頁直接呈現，並提供區塊瀏覽器連結，而非隱藏於次級頁面；
5. **教學性**：提供「詳細模式」逐步展示 commit 與 reveal 兩階段，使系統兼具技術展示與教學用途。

### 7.3 關鍵介面元件

| 元件 | 功能 |
|---|---|
